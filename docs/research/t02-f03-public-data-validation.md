# T02 · F03 공공데이터 검증 기록

- 확인일: 2026-09-17
- 범위: 답십리 → 홍대입구, 동대문역사문화공원 환승과 을지로4가 대체 환승
- 상태: 승강장 정보 응답 확인, 나머지 API별 활용신청 대기

## 먼저 내린 결론

KRIC의 표준 이동경로 API는 출발역 진입, 환승, 도착역 퇴장을 **방향 조건이
있는 순서 데이터**로 조합하는 F03의 기반으로 사용할 수 있다. 다만 공개 명세만으로는
`elvtSttCd`의 코드 의미, 시설 고유 식별자, 상태 관측 시각과 갱신 주기를 확인할 수
없다. 따라서 현재 자료만으로 “고장 난 특정 엘리베이터를 실시간으로 제외했다”고
표시하면 안 된다.

첫 구현은 다음처럼 경계를 나눈다.

1. 검증된 정적 이동경로로 지상 → 승강장 → 환승 → 지상 여정을 조합한다.
2. 시설 상태는 `operational`, `out_of_service`, `unknown`으로 분리한다.
3. 관측 시각과 시설 ID가 없는 상태 코드는 `unknown`으로 처리한다.
4. `out_of_service`가 신뢰 가능한 별도 출처에서 들어온 경우에만 해당 시설과 연결
   구간을 제외하고 대체 환승을 계산한다.

KRIC API는 JSON/XML REST 형식이며 포털 명세에 `활용신청`과 `serviceKey`가
표시되어 있다. KRIC 소스의 이용허락범위는 포털에 `저작권표시`로 기재되어 있으므로
앱과 데이터 패키지에 출처를 남긴다.

## 2026-09-17 실제 호출 결과

`apps/api/.env`의 `KRIC_SERVICE_KEY`를 노출하지 않고 17개 표본 요청을 검사했다.
KRIC는 HTTP 200 안에 자체 결과 코드를 담으므로 `header.resultCode`까지 확인해야 한다.
수집기는 `resultCode="00"`만 성공으로 판정하고, 그 외에는 종료 코드를 실패로 반환하도록
수정했다.

| API | 표본 | 결과 | 판정 |
| --- | --- | --- | --- |
| `convenientInfo/stPlf` | 답십리 5호선, 동대문역사문화공원·을지로4가 2호선 | `00 정상 처리` | 현재 키로 사용 가능 |
| `vulnerableUserInfo/stationPlatformTrainDistance` | 답십리 1·2번 승강장 | `30 등록되지 않은 서비스키` | 이격거리 API 활용신청 필요 |
| 노선·진입·환승·엘리베이터 관련 나머지 표본 | 대표 여정 12건 | `30 등록되지 않은 서비스키` | 각 API 활용신청 필요 |

답십리 승강장 정보는 2건이 반환됐다. 두 승강장 모두 지하 3층 상대식 승강장이며,
`plfNo=1/updnDvCd=1`과 `plfNo=2/updnDvCd=2`가 확인됐다. 스크린도어는 있음,
안전발판은 없음으로 응답됐다. 방향명은 이 응답에 없으므로 노선 순서 또는 이동경로
응답과 결합하기 전에는 1·2번 승강장을 임의로 마장 방면이라고 표시하지 않는다.

이번 결과는 **키가 전부 잘못된 것이 아니라, 승강장 정보 서비스에는 등록되어 있으나
다른 서비스에는 아직 등록되지 않은 상태**로 해석한다. 원본 응답은 Git에서 제외된
`data/research/t02/raw/`에 보관했다.

## 대표 여정 방향 조건

아래 코드는 서울교통공사 역번호 체계를 바탕으로 만든 **수집 후보**다. 실제 사용 전
`subwayRouteInfo` 응답에서 역명·호선·운영기관·인접 순서를 다시 대조한다.

| 구간 | 후보 요청 조건 | 확인하려는 것 |
| --- | --- | --- |
| 답십리 진입 | 5호선 `stinCd=542`, `nextStinCd=541`(마장) | 홍대입구 방면으로 가는 승강장 진입 동선 |
| 동대문역사문화공원 환승 | 출발 5호선 `stinCd=536`, 대상 2호선, 대상선 인접역 `206`(신당)·`204`(을지로4가) | 2호선 홍대입구 방향 환승 단계와 포함 시설 |
| 을지로4가 대체 환승 | 출발 5호선 `stinCd=535`, 대상 2호선, 대상선 인접역 `205`(동대문역사문화공원)·`203`(을지로3가) | 동일 목적지로 이어지는 대체 환승 단계와 포함 시설 |
| 홍대입구 퇴장 | 2호선 `stinCd=239`, `nextStinCd=238`(합정) | 해당 진행 방향에서 승강장→지상 퇴장 동선 |

`transferMovement`의 공식 충무로 예시는 현재 선·역과 함께 환승 대상선 양쪽의 인접
역 코드를 전달한다. 따라서 `prevStinCd`를 출발선의 직전 역이라고 단정하지 않고,
실제 응답과 공식 문의로 의미를 확정한다.

요청 목록은 [`tools/kric/t02-queries.json`](../../tools/kric/t02-queries.json)에
기계 판독 가능한 형태로 기록했다.

## 화면 표현 결정

첨부된 철도역 편의정보의 복잡한 역사 그림은 원본 검증 자료로 사용하되, 앱의 기본
안내는 아래처럼 순서가 있는 텍스트 카드로 변환한다.

1. **진입:** `2번 출구 옆 엘리베이터를 타고 B2 대합실로 이동하세요.`
2. **개찰:** `교통카드를 태그한 뒤 마장 방면 엘리베이터를 이용하세요.`
3. **승강장:** `B3 마장 방면 승강장으로 이동하세요.`
4. **탑승:** 권장 차량·문과 엘리베이터 인접 위치를 함께 표시한다.
5. **주의:** 해당 문 위치의 승강장 이격거리를 낮음·주의·높음으로 표시한다.
6. **환승:** 환승이 있으면 하차 위치부터 다음 승강장까지 `transferMovement` 단계를
   이어 붙인다.
7. **퇴장:** 마지막 역의 승강장부터 지상 엘리베이터까지 순서대로 표시한다.

이격거리 색상만으로 위험을 전달하지 않는다. 첨부 화면의 구간 기준은 `0~10`,
`10 초과~15`, `15 초과`로 보이지만, 공식 API 명세에 `sfDst` 단위가 적혀 있지 않으므로
단위와 경계 포함 규칙을 확인하기 전에는 제품 문구에서 수치 단위를 단정하지 않는다.

## 누락과 위험

- 표준 이동경로 응답에는 `elvtSttCd`가 있지만 포털 페이지에서 코드값 의미를 찾지
  못했고, 상태 관측 시각도 출력 항목에 없다.
- `mvPathMgNo`는 이동경로 관리번호이지 승강기 일련번호라고 명시되어 있지 않다.
- 인접 차량·문 API는 승강장번호를 주지만 방향을 직접 주지 않는다.
- 정적 엘리베이터 파일은 상태와 기준일을 포함하지만 현재 고장을 반영하는 자료가
  아니다.
- 서울시 지상 위치 데이터는 내부 층·개찰구·승강장 연결을 제공하지 않는다.
- 따라서 동대문역사문화공원 고장 시 을지로4가를 선택하는 규칙은 두 환승 동선의
  완결성과 시설 식별자를 확인한 다음, 신뢰 가능한 상태 소스를 연결해야 활성화한다.

## 다음 검증 절차

1. KRIC에서 노선, 표준 이동경로, 표준 환승경로, 엘리베이터 이동동선·현황·인접
   차량번호, 승강장 이격거리 API를 각각 활용신청한다.
2. `npm run research:t02`로 원본 응답을 다시 수집한다.
3. 2·5호선 코드와 인접 순서를 먼저 대조한다.
4. 동대문역사문화공원·을지로4가 환승 응답이 각각 완결된 순서를 제공하는지 확인한다.
5. 답십리의 문별 `sfDst` 값과 포털 화면을 대조해 단위와 경고 구간을 확정한다.
6. 이동 단계의 경로 관리번호를 정적 시설 관리번호·승강기 일련번호와 대조한다.
7. `elvtSttCd` 코드표와 갱신 주기를 KRIC 또는 서울교통공사에 확인한다.
8. 시설 ID·상태·관측 시각을 함께 주는 소스를 확보하기 전에는 앱에 `상태 미확인`으로
   표시한다.
